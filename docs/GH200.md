# GH200 implementation notes

This is a multi-stage algorithm, not a single stateless replacement kernel.
The CUDA research paths have been compiled with CUDA 12.8.93 for SM90 and run on
an NVIDIA GH200 480GB (97,871 MiB exposed GPU memory, driver 580.105.08).
Recorded GPU tests and timings live in `results/gh200/`. These experiments do
not establish a Lean-to-CUDA correspondence or a production attention contract.

## What exists

`evaluate_blocks` evaluates numerical block envelopes from resident summaries.
`evaluate_blocks_shared` evaluates the block scalar quantities once per CTA,
then shares them across channels. `benchmark_api.cu` adds query shifts and two
screening schedules: one thread per channel with a serial block loop, and four
warps per channel with a parallel block reduction.
`reduce_and_screen` chooses a numerical BF16 candidate and tests its cell.
`scan_selected_blocks` provides a slow numerical block-correction primitive.
`screen_imported_boxes` is a separate directed-rounding checker whose inputs
must already be sound enclosures. It is not made sound by feeding it results
from the first kernel. `smoke.cu` checks the original, shared-scalar, parallel
reduction, and numerical block-correction paths. `imported_smoke.cu` separately
replays exported rational boxes and deliberate rejection controls on CUDA.

All arrays use binary64 as an explicit research choice. This is not a proposed
production storage format. No tensor-core optimization is supplied. The
prototypes favor auditable arithmetic and indexing over occupancy or throughput.
The benchmark uses a minimal C ABI with PyTorch-owned device allocations.
There is no production PyTorch operator, serving integration, concurrent work
queue, CUDA graph lifecycle manager, or fully sound GPU summary builder. The
C ABI checks dimensions and required pointers; it expects validated resident
arrays with their caller-owned sizes and identity. It is not an untrusted
summary import API. The Python benchmark builds fresh immutable summaries and
does not implement epochs, masks, cache mutation, or streaming updates.

## The intended runtime

Construct summaries once for each immutable block and reuse them. Keep original
K/V available for refinement and the declared reference fallback. Append new
tokens to a small exact tail; finalize and summarize a block when full. The
provided builder is CPU-only and its signed-moment work must be included in
setup/amortization measurements. No free streaming update is assumed.

At query time, the shared-scalar ablation shares query/centroid scores, projected
variance, radius bounds, and exponential bounds across value channels. A
coalesced channel pass evaluates contracted moments and produces an enclosure
for each `(query, block, output-channel)`. A reduction performs the two boundary
sign tests. Successful coordinates can be retained while difficult blocks are
refined, but a production output may be emitted only when its complete contract
is satisfied. Coordinate retention is not implemented as a scheduler here.

Unresolved queries populate a bounded device queue. Refine selected blocks,
intersect sound envelopes, and recheck. If the work limit, exponent range,
metadata invariant, or numerical certificate fails, invoke the declared
reference path. Use exact/interval local corrections for a rigorous path;
numerical corrections are only a performance experiment. Never label them
"exact" merely because they visit every token in a block.

For small block counts, evaluation and reduction might fit one CTA. For larger
counts, a two-pass reduction is simpler. A persistent kernel may reduce launch
cost later, but does not eliminate summary construction or fallback work.
The measured parallel reduction improves long-context, single-query device
latency substantially; it can cost more at small block counts. This does not
remove setup, fallback, or the Python decision synchronization.

## Identity and semantics

A summary must identify the owner/request, layer, KV head, data epoch, positions,
visible-token range, positional transform, precision, coordinate subset, and
value representation. An address and shape alone do not identify its contents.
Mutation, eviction, slot reuse, or RoPE changes invalidate an old summary unless
a sound update is performed. CUDA graph replay cannot reuse stale data.

Causal or sliding-window masks must be exact. Summaries for a superset of visible
keys are not valid for a masked query. Split partially visible blocks or use the
reference path. The prototype assumes an explicit partition of precisely the
visible keys, one already-scaled query, and already-transformed K/V. GQA can
share KV-head summaries while keeping per-query-head certificates separate.

An exact-real attention certificate does not imply bitwise agreement with
FlashAttention or another chosen kernel. The latter has its own accumulation,
exp approximation, intermediate precision, and output-cast contract. Reference
roundoff bounds or a formally matched implementation are prerequisites for a
bitwise substitution. The signed-zero bit pattern also lies outside the current
numerical BF16 model.

## Reproduce the GPU build and validation

The Grace Hopper system has a Hopper GPU. Use its actual device capability and
installed toolkit rather than inferring flags from the CPU architecture [1,2].
The following targets ordinary SM90 features and does not require SM90a-only
instructions:

```sh
nvidia-smi --query-gpu=name,compute_cap --format=csv
nvcc --version
.venv/bin/cmake -S kernels -B build/gh200 \
  -DCMK_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=90 \
  -DCMAKE_BUILD_TYPE=Release
.venv/bin/cmake --build build/gh200 -j
build/gh200/cmk_cuda_smoke /tmp/cmk-fixture.bin
build/gh200/cmk_cuda_imported /tmp/cmk-imported.txt
compute-sanitizer --tool memcheck --error-exitcode 99 \
  build/gh200/cmk_cuda_smoke /tmp/cmk-fixture.bin
compute-sanitizer --tool memcheck --error-exitcode 99 \
  build/gh200/cmk_cuda_imported /tmp/cmk-imported.txt
```

Both memcheck commands completed with zero reported errors. The numerical
fixture has 48 passing coordinates, a maximum scaled CPU/GPU envelope difference
of `2.83e-16`, and a full block-correction absolute error of `8.88e-16`. Shared
scalar envelopes agree exactly with the original on this fixture; the parallel
reduction changes candidates by at most `2.22e-16`.
Racecheck reported zero hazards, errors, or warnings, and synccheck reported
zero errors on the numerical smoke paths. Four invalid dimension/pointer cases
are rejected by the benchmark ABI before launch. The sanitizer logs are retained;
`ptxas_resources.log` records register/shared-memory usage and no spills for
these kernels. This is compiler resource information, not measured occupancy.

The imported fixture has 160 rows: CUDA retains all 74 rows certified by the
rational residual oracle and rejects 13 additional malformed, overflow, and
strict-boundary controls. Each oracle-certified fixture row was independently
checked against rational attention before export. This is experimental evidence
for the directed checker, conditional on the sound imported boxes, not a proof
that arbitrary numerical summary outputs are sound. Sanitizers establish only
the properties checked on these runs.

Do not enable fast math for a certificate without re-establishing its numerical
contract. NVIDIA documents directed binary64 arithmetic separately from the
ordinary elementary functions [3]. A round-to-nearest `exp` is not an outward
exponential enclosure.

## Reproduce the measured attention experiment

```sh
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 .venv/bin/python scripts/benchmark_gpu.py
# After reproducing scripts/model_traces.py's pinned model capture:
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 .venv/bin/python scripts/benchmark_gpu.py \
  --trace results/model_traces/gpu_prose_4096_layer0.npz \
  --trace results/model_traces/gpu_prose_4096_layer12.npz \
  --trace results/model_traces/gpu_prose_4096_layer23.npz
```

The recorded sweep uses 57 synthetic configurations and nine actual trace/rank
configurations. It varies `N=1024,8192,32768`, retained rank `0,4,16` (plus a
full-rank check), key spread, and `Q=1,32`, with `d=h=64` and blocks of 256 keys.
`Q=1` is a single decode query; `Q=32` is a noncausal shared-KV query batch.
Neither is a complete serving benchmark. Traces are actual post-RoPE arguments
from pinned Qwen2.5-0.5B weights, with seven query heads sharing one KV head at
the final visible prefix position. Model capture and all-head diagnostics have
their own manifest and limitations in `results/model_traces/`.

Synthetic inputs are rounded to BF16, then represented exactly in binary64 for
the summary path. The dense baseline is PyTorch 2.7's **forced FlashAttention
SDPA backend**, consuming those same BF16 values with `scale=1`, no dropout and
all supplied keys visible. A binary64 softmax/matmul baseline supplies an
independent numerical output check. Its result is not an exact-real oracle;
FlashAttention has a distinct accumulation/output contract. Any accepted-output
mismatches against either baseline are reported separately.

All GPU arrays and output workspaces are resident for query timing. Summary
construction, upload, input upload/casts, workspace allocation, graph capture,
workspace bytes, and summary bytes are recorded separately. CPU summary array bytes exclude group indices and Python object/hash overhead;
they include value extrema used by the optional Python coupling extension; the CUDA
path does not use those extrema, and `gpu_summary_bytes` reports its actual
resident arrays. The full pipeline includes three launches, screening, a device
boolean reduction, CPU synchronization, and either a BF16 output cast or a full
batch FlashAttention fallback. One failed coordinate triggers full-batch
fallback; there is no claim of a device-resident adaptive scheduler.

Each ordinary timing records seven sets of 20 calls using CUDA events and host
wall time. Fixed-input CUDA graphs separately remove Python launch gaps; they
contain only the indicated resident computation and report capture costs.
Graph replay is an optimistic microbenchmark, not the measured adaptive path.
End-to-end ratios compare the complete eager path to the eager dense baseline;
graph ratios compare graph mode with graph mode. Setup amortization is computed
from the measured reusable setup and complete per-batch query cost. A null
break-even means no finite reuse count helps at the measured query costs.

The initial scalar-only sweep is retained in
`results/gh200/benchmark_scalar_only.json`. The final sweep includes original,
shared-scalar, and parallel-reduction timings under the same inputs. Initial
absolute-tolerance validation failures on very broad trained residuals are
retained in `validation_failures.json`; the final check uses a `1e-12` scaled
tolerance, requires identical screen decisions, and separately checks outputs
against binary64 attention. This change does not turn numerical residuals into
directed intervals.

A second 66-case run at commit `d2c3668` is saved in
[`reproduction.json`](../results/gh200/reproduction.json), with before/after
source, library, and trace hashes in
[`provenance.json`](../results/gh200/provenance.json). It reproduces every
coverage and mismatch count. Parallel-screen graph medians range from −1.08%
to +1.42% of the original; host-wall measurements vary more for both methods.
Every complete screened path remains slower and every break-even remains null.
The original sweep supplies the paper's plots and tables; both runs are retained.

## What the measurements explain

For the tight rank-four case, fixed-input graph device times in microseconds are:

| N / Q | Original | Shared scalar | Parallel reduction | Dense FlashAttention |
| --- | ---: | ---: | ---: | ---: |
| 1024 / 32 | 20.47 | 19.87 | 20.84 | 9.80 |
| 8192 / 1 | 35.69 | 35.60 | 18.72 | 14.55 |
| 32768 / 1 | 118.65 | 118.14 | 20.09 | 31.30 |
| 32768 / 32 | 143.28 | 147.52 | 64.89 | 34.21 |

The favorable `32768 / 1` device result still takes `83.11 µs` for the complete
host-decision path versus `35.62 µs` for the eager dense baseline, before about
50 ms of reusable summary setup. Every measured complete pipeline is slower
than the dense baseline; every reported amortization break-even is null. The
fixed-graph result is therefore evidence about a kernel bottleneck, not a
profitable attention replacement.

Sharing scalar work alone helps little because the original screen places an
entire block loop on one thread per output coordinate. For a single query this
launch uses only one CTA for 64 channels. The parallel reduction instead uses a
CTA per coordinate, exposing block work to more SMs. It changes summation order
and is used only by the numerical path. Its synchronization and extra CTAs can
hurt at small block counts, and higher query counts already expose more work.

Tight synthetic clusters are a favorable witness distribution, not a coverage
estimate for trained attention. Moderate/broad controls, outputs centered near
zero, exact BF16 midpoints, and trained traces remain visible in the results.
The trained traces show why small candidate error is insufficient: the
worst-case score-radius and signed-moment envelopes must fit a narrow rounding
cell for every output coordinate.

## Remaining experiments

Extend the recorded all-layer/head Qwen2.5-0.5B probes to larger models,
independent corpora, decode steps, and additional exact masks. Record summary bytes, setup work, retained rank,
per-query bound widths, whole-output pass rates, fallback fractions, and worst
cases. Report negative controls and near-midpoint behavior. Synthetic clusters
do not estimate trained-model coverage.

Then compare against the fastest appropriate dense decode implementation on the
same GH200, not against the scalar fallback in this repository. Count creation,
updates, allocations, launches, screening, and fallback. Keep dtype, batch,
context, causal semantics, graph mode, warmup, and timing synchronization equal.
Measure the full serving path separately from an attention microbenchmark.

The next implementation question is removing the host decision and selecting
the reduction schedule by workload, while retaining sound metadata requirements.
Low-rank summaries are useful only when their explicit discarded-score error is
small enough. Reuse, cheap witnesses, and certification rate must all cooperate.
The recorded complete GH200 pipeline is slower than the measured dense baseline
even in favorable cases. A resident device microbenchmark can be faster at a
long single-query context; that saving does not establish end-to-end benefit.
